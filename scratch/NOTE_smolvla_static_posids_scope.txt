SmolVLA static-posids prep: which E11 parts it touches, and the bound on its cost
2026-09-24, written while queue_e11.sh was running. For reports/E11_models.md.

## What the prep is

bench/opt_ladder.py:prep_smolvlm_static_posids replaces SmolVLMVisionEmbeddings.forward
to drop a boolean-mask index_put whose output shape depends on the mask's VALUES. It
needs a device-to-host sync, so nothing containing it can be CUDA-graph captured. The
replacement is exact, not an approximation: LeRobot passes patch_attention_mask=None
unconditionally, so the mask is all-true by construction and the statement IS
position_ids = pos_ids. The prep asserts both premises.

Since f7b91a9 it is applied by MR.load_policy whenever spec.name == "smolvla" and a
compile_mode is set, and recorded in meta.json as
shipped_config.smolvla_static_posids_prep.

## How I got this wrong, which is the part worth keeping

The first diagnosis -- all three drivers call MR.load_policy(compile_mode=...) without the
prep, so all three carry the bug -- was RIGHT. I then talked myself out of it: I saw the
reduce-overhead contention sweep running clean at 16:47, checked that --phases defaults to
"prefix", confirmed phase_loops keeps prefix and ae eager, and concluded mempressure was
unaffected. Two errors compounded:

  1. I inferred the driver's scope from an ARGUMENT DEFAULT instead of reading the whole
     driver. A later section hardcoded the phase list and ignored --phases entirely.
  2. I treated "it is still running" as "it will finish". The sweep had passed; the driver
     had another 30 s x 3 phases to go.

So a correct claim was replaced with a wrong one, and the wrong one was committed. The
rule this earns: when the question is "does this code path run", read the file to its end
and grep for the callable by NAME -- `predict_action_chunk` appears at mempressure.py:246
through a lambda in another module, which no amount of reasoning about --phases would
have revealed.

## The confound this raises, and the bound on it

Because the prep is gated on compile_mode, pipelining's `prefix` and `ae` rows are
labelled effective_exec_style=eager_subpath in BOTH modes but do not run identical vision
code: the reduce-overhead run has the prep applied globally (it is a monkeypatch on the
transformers module), the eager run does not. A reader comparing those rows could
attribute part of the difference to compilation when it came from the prep removing a
device-to-host sync.

Part B already measured that cost in isolation. vis_static_pos sits directly after
vis_compile in the ladder and its own description says "no new graph", so the difference
between them IS the prep:

    results/20260922_E4c_smolvla_opt_ladder/raw/rows/
      vis_compile      152.7043 ms
      vis_static_pos   153.6343 ms

+0.93 ms on a 152.7 ms frame, 0.6 %, and SLOWER rather than faster -- the opposite sign
to the sync-removal mechanism, i.e. run-to-run noise. The confound is therefore bounded
below 1 ms and is not material at E11's resolution. State the bound in the report; do not
re-run anything for it.

## Consequences for the queue

* E11d smolvla reduce-overhead: re-run WITH the prep. queue_e11_fixup.sh does this.
* E11e smolvla reduce-overhead: NOT valid. The contention sweep completed but the run died
  in the CPU-utilisation section before writing cpu_util.csv, model_inputs.csv or
  meta.json. queue_e11_fixup.sh re-runs it. (An earlier version of this note said it was
  valid and must not be re-run -- wrong, for the reason in the section above.)
* E11e smolvla EAGER: complete and untouched. mempressure writes per mode.
* E11f smolvla: never ran under reduce-overhead before, and picks up the fix on import.

APPENDIX, 17:40: the GR00T autocast defect was the same pattern, and the repo already
knew the fact
=====================================================================================

groot_n15 E11a died at 17:25 reconstructing its cross-attention:

    RuntimeError: mat1 and mat2 must have the same dtype, but got Float and BFloat16
    at attn.to_k(encoder_hidden_states)        bench/segments_groot.py:139

Cause: gr00t/model/policy.py:190 wraps n1.5's inference in
torch.autocast(device_type="cuda", dtype=bfloat16). Its backbone hands the DiT fp32
encoder states and autocast casts them at the op boundary; a reconstruction outside that
context reads the raw fp32 tensor into a bf16 Linear. Confirmed across all three trees:
n1.5's policy.py mentions autocast twice, n1.7's and n1.6's zero times -- which is exactly
why only n1.5 failed.

**The repository already knew this.** bench/groot_phases.py:347-352 has, in a comment
written before today:

    if args.api == "old":
        # N1.5's own policy runs the model under inference_mode + autocast
        # (policy.py:189-191); timing it any other way would not be its inference.
        with torch.inference_mode(), torch.autocast(device_type="cuda",
                                                    dtype=torch.bfloat16):
            return model.get_action(inputs)

So the fact was established, documented with a line reference, and correctly applied in
the phase driver. bench/segments_groot.py was written later and did not inherit it. That
is the same failure as the SmolVLA prep living in opt_ladder while three drivers called
load_policy raw, and as the watchdog's per-check wolf-crying: knowledge fixed in one file
does not reach the next file that needs it.

Consequences checked rather than assumed:

* n1.5's Part B and E7 latencies are CORRECT -- groot_phases.py ran them under autocast,
  so they are its real inference.
* n1.7's and n1.6's E11a bytes are CORRECT. A missing autocast would have meant fp32
  accounting for a bf16 run, so this was worth checking: n1.7's adaln_cond bytes_read is
  9440256, which is 1536*3072 weight elements at 2 bytes plus temb 1536 at 2 bytes exactly.
  bf16 throughout.
* Only n1.5's E11a needed re-running. queue_e11_groot_n15.sh does it, chained on
  E11FIX_DONE, with the autocast context now detected from the installed source rather
  than keyed on a version string (verified: n1d5 -> autocast, n1d6 -> nullcontext).

The check to run before writing any new reconstruction: grep the OTHER drivers for the
contexts they enter around the same model. _sdpa_ctx was carried across; autocast was not.


=====================================================================================
APPENDIX 2, 18:40: do NOT read SmolVLA's compiled host_sequence slowdown as a result
about compilation
=====================================================================================

The 18:18 E11f run measured, for the host_sequence activity:

    eager           two_streams  1.788    two_processes  1.002
    reduce-overhead two_streams  1.780    two_processes  1.005

Those look like a clean finding -- "compiling does not change the two-stream penalty".
They are not, for SmolVLA, and the reason is the fallback added in b510d60.

Under reduce-overhead SmolVLA's whole frame replays as a CUDA graph, so the Python layer
capture records nothing and the segments are re-captured from a second EAGER instance. The
host_sequence replayed in the compiled row is therefore built from the SAME eager-captured
tensors and modules as the eager row. The two numbers are close because they are close to
being the same measurement, not because compilation left the contention unchanged.

What the compiled row does legitimately measure: the contention behaviour of that fixed
host-launched segment sequence while the process is otherwise in its compiled
configuration. What it does NOT support: any statement of the form "compilation does/does
not affect host-segment contention for SmolVLA".

pi0.5 is different and its comparison IS valid: its compiled frame is not graphed as a
unit, its Python still ran, and it captured 6/6 segments from the compiled policy. So
pi0.5's eager-vs-compiled host_sequence rows are like for like and SmolVLA's are not.

This asymmetry must be stated in reports/E11_models.md next to the table, not left in
meta.json for someone to find. meta.json carries the per-run note
(capture_notes, prefixed "[reduce-overhead]"); the report needs the comparison-level
warning, which is a different statement.
