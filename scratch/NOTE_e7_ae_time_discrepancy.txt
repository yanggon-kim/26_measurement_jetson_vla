The prefix agreeing to 0.24 % says the harness, the rung, the checkpoint and the gate are

Checked and ruled out: bench/phase_builders.make_ae's body is structurally IDENTICAL to
bench/corun.py's expert_stage -- same bounded Python loop, same per-step
`torch.tensor(t, device=...)`, same `x_t = x_t + dt * v_t`, same single cache built once by
prefix_once, same single noise tensor. N is 10 in both. The code is not the difference.

Corroboration that E7's figure is not a typo: E5's pi0 best ae_step region is 197.39 ms
profiled at an inflation of about x1.17, i.e. roughly 168 ms unprofiled, which matches E7's
167.36. So both of E7's own measurements agree with each other and disagree with mine.

## Hypothesis: E7's own power sampler inflates it, because this phase is GIL-bound

bench/power_core.py defines `class Rails(threading.Thread)` -- a daemon thread sampling four
sysfs rails at 20 Hz -- and E7's `ae` numbers were measured with it running.

E12 has now MEASURED that this workload is CPU-issue-bound: host issue/wall = 1.0000 over a
99.5-second run, consistent with E5's 84.2 % GPU idle over 968 kernels/step. A workload whose
wall clock is entirely Python issuing kernels is exactly the workload a 20 Hz Python sampler
thread would slow, by taking the GIL away from the issue loop.

E7 did check its sampler's cost and found 2 %: `full` 722.55 ms with it against Part B's
711.75 ms without, at N = 4. But at N = 4 `full` is prefix-dominated (A = 249.92,
B = 67.18), and the prefix is fewer, larger kernels. A sampler can cost 2 % on a
prefix-dominated frame and much more on the expert alone. The 2 % check does not cover the
`ae` phase, and nothing else does.

## Why this matters beyond bookkeeping

If the hypothesis holds, then E7's **`ae` phase times are inflated** and three things follow:

1. **`r = A_iso / B_iso` is wrong.** E7 gives 1.50 at N = 10 (251.28 / 167.36). With
   B_iso = 111.01 it is 2.27. `r` is the break-even the ENTIRE E12 question is compared
   against -- "s < r means the expert is not the bottleneck" -- so the threshold itself moves.
   E12's own reports use the in-session `r` (§3 requires it), so E12's conclusions are not
   affected, but anyone quoting 1.50 from E7 would be using an inflated denominator.
2. **E7's "the expert is the CHEAP phase" finding needs re-checking.** Its energy figures are
   mean power x region time, so an inflated region time inflates the integrated energy too
   and the energy-to-time RATIO may be largely unaffected -- but the absolute per-phase times
   and the A:B split are what the PIM argument quotes.
3. It would be a **third instance tonight of a measurement artefact that favours a
   conclusion**: the expert looking slower makes the expert look more worth accelerating.

UPDATE 05:55 — the sampler hypothesis is FALSIFIED. The gap is something else.
=====================================================================================

Same expert code, three interference conditions, 45 s each, bf16_both, N = 10:

    sampler=none              111.02 ms   n=406
    sampler=rails             111.22 ms   n=404   (+0.18 %)
    sampler=rails+tegrastats  111.23 ms   n=405   (+0.19 %)

**The sampler costs 0.19 %, not 50 %.** E7's Rails thread and tegrastats subprocess do not
explain the 33.67 % gap. The reasoning was plausible -- this phase IS CPU-issue-bound
(issue/wall = 1.0000), so a 20 Hz GIL-taking thread SHOULD have hurt it -- and it is wrong.
Apparently 20 Hz is simply too slow to matter against an issue loop running flat out; the
thread sleeps ~50 ms between samples and holds the GIL for microseconds.

Also established, incidentally: the baseline reproduces to 111.01 / 111.02 / 111.22 / 111.23
across four separate processes. Run-to-run variation is NOT the explanation either. The gap is
systematic, and both sides are internally reproducible -- E7's 167.36 is corroborated by E5's
independent nsys measurement (~168 ms), and mine agrees with itself to 0.01 ms.

## Next candidate: process state, not measurement overhead

E7's power_phases.py measures **idle -> prefix -> ae -> full, sequentially in ONE process**.
By the time its `ae` loop runs, the prefix's compiled graphs, its CUDA-graph memory pool and
a fragmented caching allocator are all resident. My two-process harness measures the expert
in a **fresh process** that has only ever run a prefix once, to build one cache.

That is a real difference and it is the right next thing to test, because it predicts a
direction: more resident state should make the expert SLOWER, which is the sign of the gap.

The test: run a prefix LOOP in the same process before timing the expert, replicating E7's
sequence, and see whether 111 ms moves toward 167 ms. If it does, E7's `ae` number is a
measurement of the expert *after* the prefix phase rather than of the expert alone -- which is
a legitimate thing to measure and simply not the same quantity, and it would need saying in
both reports rather than "correcting" either.

Still do NOT quote E7's r = 1.50 as though reconciled. The discrepancy is now BETTER
characterised and still unexplained: one hypothesis tested and rejected, one named and
untested.
