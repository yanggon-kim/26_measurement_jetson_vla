E7 `ae` vs E12 isolated expert: RESOLVED 2026-09-25.

THE GAP
  E7 (results/*_E7_pi0_*, bf16_both, N=10, MAXN): ae = 167.36 ms
  E12 isolated expert (bench/corun_2proc.py, same rung/N/mode): 111.01 ms
  ratio 1.508 (+50.8 %). The prefix matched to +0.24 % (251.89 vs 251.28), so the
  discrepancy was specific to the expert stage.

WHAT IT WAS NOT (both measured, both rejected)
  1. E7's samplers. power_core.measure() runs a 20 Hz Rails PYTHON thread (takes the GIL
     from the kernel-issue loop) and a tegrastats subprocess at 100 ms. Same expert code
     under all three conditions:
         none                111.02 ms
         rails               111.22 ms  (+0.18 %)
         rails+tegrastats    111.23 ms  (+0.19 %)
     0.19 %, not the ~50 % required.
  2. In-process residency. power_phases.py:187 is `for phase in ("prefix","ae","full")`,
     all three sequentially in ONE process, so E7's `ae` loop inherits the prefix's
     compiled graphs, CUDA-graph memory pool and a fragmented caching allocator, while my
     harness measured the expert in a fresh process. Replicated with --preheat-prefix 60
     (238 prefix iterations before timing, same process):
         fresh process       111.02 ms
         after prefix loop   111.34 ms  (+0.29 %)
     0.29 %. Rejected. Note this hypothesis predicted the right DIRECTION, which is why it
     was worth running -- direction agreement is not magnitude.

WHAT IT WAS
  The only remaining difference between the two code paths was one line. E7's
  phase_builders.make_ae builds the timestep tensor INSIDE the denoise loop:

      tt = torch.tensor(t, dtype=torch.float32, device=x_t.device).expand(bsize)

  while bench/corun.py's expert_stage precomputed them via timestep_tensors().
  torch.tensor(<python float>, device="cuda") copies from PAGEABLE host memory, which is
  blocking: the host waits until the copy lands, i.e. until the stream has drained every
  kernel queued ahead of it. On a launch-bound stage the CPU normally runs far ahead of
  the GPU; this discards that run-ahead once per denoise step.

  Controlled swap -- corun_2proc.py --e7-timesteps, everything else identical:
      precomputed timesteps   111.02 ms
      E7's per-step tensor    167.09 ms   <- E7 reports 167.36 ms, agreement 0.16 %

  Cost: 56.07 ms of 167.09, i.e. 33.6 % of the expert stage at N=10, or 5.6 ms per
  denoise step. That per-step figure is far too large for a 4-byte copy, which is the
  evidence that the mechanism is the DRAIN and not the transfer. I did not separately
  instrument the drain (e.g. nsys on the stall); the controlled swap is the evidence, and
  the mechanism above is the explanation for it.

WHOSE FAULT
  NOT E7's. lerobot modeling_pi0.py:858-859 in the shipping sample_actions does exactly
  the same thing:
      time = 1.0 + step * dt
      time_tensor = torch.tensor(time, dtype=torch.float32, device=device).expand(bsize)
  So E7's make_ae faithfully reproduces the shipping model, E7's 167.36 ms is a correct
  measurement of it, and r = A/B = 1.50 STANDS and may now be quoted.

  The defect is in E12's reporting. reports/E12_pi0_corun.md §6 stated that precomputing
  the timestep tensors is "not labelled, because §7 names it as the example of a permitted
  harness fix." That was written believing the change was free. It is worth 33.6 % of the
  expert stage. §7 permitting the CLASS of change does not make an unlabelled 33.6 %
  speedup acceptable -- it is now labelled wherever E12's expert numbers appear.

CONSEQUENCES
  1. A second free optimisation to shipping pi0, independent of E12 and simpler than the
     att_masks de-sync: hoist the N constant timestep tensors out of the denoise loop.
     Worth 33.6 % of the expert stage at N=10, bf16_both, MAXN.
  2. Together with the att_masks syncs (E12 §3), pi0's per-frame host-blocking operations
     are 1+N att_masks conversions AND N pageable timestep copies. This STRENGTHENS E12's
     conclusion rather than altering it: the shipping model is built in a way that hands
     the GPU back to the host N times per frame, which is why nothing overlaps.
  3. E12's own conclusions are unchanged in direction: T_pipe = A_iso + B_iso and
     issue/wall = 1.0000. Removing host-blocking work makes a stage faster; it did not
     make the pipeline overlap.

SEPARATE FINDING, recorded so the claim is not left over-broad
  The att_masks de-sync (patch_pi0_nosync) does NOT survive torch.compile. Under
  bf16_both it raises "Error: accessing tensor output of CUDAGraphs that has been
  overwritten by a subsequent run" -- the memoised tensor is allocated inside the compiled
  region on the first call, so it becomes a CUDAGraph output and cannot be reused. The
  19 % figure in E12 §3 is EAGER, which is what E12's MAXN run used. §3's "worth taking
  regardless of how the co-run question resolves" needs that caveat: as implemented it is
  eager-only. A compile-safe version would allocate the tensors outside the compiled
  region.
